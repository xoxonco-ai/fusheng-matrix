# 跨檔計算層重複

## 現狀

`hepan.html` 自帶一整套計算層，與 `paipan.html` 重複約 14 項。
**目前零行為漂移**——但那是運氣，不是機制。

## 逐項比對結果

| 項目 | 跨檔狀態 |
|------|----------|
| `GATE_ORDER`、`GATE_CENTER`、`CHANNELS`、`MOTORS`、`gco` | 逐字相同 |
| `_SG`、`_fmt`、`_CNM` | 逐字相同 |
| `sunLon` | 逐字相同 |
| 五行天干表、地支表 | 逐字相同 |
| 土星回歸（關卡年） | 逐字相同 |
| 閘門轉換 | 命名不同（`lonToGate` / `_ltg`），行為一致 |
| `planetLon` | 只差被呼叫者名（`trueNodeLon` / `_tnode`），改名後逐字相同 |
| 北交點 | 只差參數名（`date` / `dt`），改名後逐字相同 |
| 紫微時辰索引 | 內容相同；paipan 已抽成函式，hepan 仍就地展開 |
| 設計盤二分 | 行為一致；paipan 已抽成函式，hepan 仍就地展開 |

### 驗證方式

- 閘門轉換：從兩個檔案抽出實作送進 `vm`，掃 29,377 個黃經值（含 64 個閘門
  邊界 ±1e-9 與每爻邊界）→ 0 不一致
- 設計盤：3 種確定性 `sunLon` 替身 × 292 個跨百年時刻 = 876 次 → 0 不一致
- 紫微時辰索引：h=0..23 → 0 不一致
- `planetLon`、北交點：把命名差異正規化後逐字比對 → 相同

## 已於 2026-11-10 收斂（選了 A）

抽出 [[fusheng-calc.js（共用命理計算層）]]，兩頁都 `<script src>` 引入。
19 個頂層宣告從兩份變一份，`paipan.html` −3,384 字元、`hepan.html` −2,867 字元。

一併收進共用檔的，比原先盤點的還多：關卡年的 `saturnReturn` 與 `chongYears`
（土星回歸與流年沖日支在兩檔逐字相同，各 380 / 221 字元）。

### 最大的風險面不是演算法，是宣告衝突

classic script 的頂層 `const` 與 inline script **共用同一個全域詞法環境**。
共用檔和頁面若宣告同名變數，整個 inline 區塊會因 SyntaxError 完全不執行
——不是只壞那一行，是整頁的互動全死。

擋法：抽出共用檔與兩頁 inline 的頂層宣告名稱做交集，必須為空。
兩頁交集皆為 0，且頁面引用的共用名稱（14 / 15 個）全部有定義。

### 驗證

| 層次 | 範圍 | 結果 |
|------|------|------|
| 靜態 | 宣告衝突交集、未定義引用 | 0 / 0 |
| 語法 | 共用檔與兩頁 inline | `node --check` 全過 |
| 端對端 | paipan 6 組渲染 DOM ＋ 摘要 | 改動前後逐字相同 |
| 端對端 | hepan 6 組 `calcPerson()` ＋ 5 組 `quickRead()` 合盤 | 改動前後逐字相同 |
| 跨頁 | 同一個人在單人盤與合盤的人類圖類型／權威／角色 | 5 組全一致 |

共 23 項比對，零差異，兩頁皆無新增 page error。

跨頁那一項在收斂前也是一致的（副本內容相同），差別在於**現在是結構上保證，
不再是巧合**。

## 當初評估的三個選項（已選 A）

| 選項 | 做法 | 代價 |
|------|------|------|
| A | 抽出 `fusheng-calc.js`，兩頁都 `<script src>` 引入 | 要動兩頁的 script 標籤與載入順序；根治 |
| B | 只把 hepan 對齊 paipan 的函式形式 | 便宜；跨檔問題仍在，只是形式一致 |
| C | 維持現狀，只記錄 | 零成本；下次有人改演算法就會踩到 |

**傾向 A**：兩頁都是獨立 HTML、沒有打包工具，而 repo 已經有
`supabase-config.js`、`fusheng-widget.js` 這種「外部 JS 檔 + script 標籤」
的既有模式，照著做即可，不需要引入建置流程。

A 的風險在載入順序——計算層必須在 inline 區塊之前就緒，
且 `Astronomy` / `Solar` / `iztro` 要先載入。目前四個 CDN 標籤都在
inline 區塊之前，把 `fusheng-calc.js` 插在它們之後、inline 之前即可。
